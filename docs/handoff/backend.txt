БЭКЕНДЕРУ — ПЕРЕДАЧА ТЕКУЩЕЙ СБОРКИ LLH_BY_KARMA
Целевая ветка: main. Все пути ниже — относительно корня репозитория.
Основа: backend 49303e2 + исправления интеграции и разбалловки.
Это демонстрационная сборка; независимый тестировщик проверяет её 11 октября 2026.

1. ТЕСТИРОВАНИЕ И БАЛЛЫ
Файл: backend/app/services/testing_engine.py.
Новый тест: ровно 3 code-задачи выбранного направления и грейда.
Выбирается по одной easy, medium, hard, именно в этом порядке.
Идентификаторы банка используют mid; API показывает medium.
Матрица: 15+5=20, 20+10=30, 35+15=50.
База пропорциональна passed/total; бонус только за все тесты.
Общий балл округляется до одного знака; балл задачи — до двух.
План 5/3/2 не используется для новых попыток. Старые сохранённые попытки без новых
весов продолжают считаться по старой структуре, чтобы не ломать историю.
В разборе сохраняются fraction (0..1), score (баллы), веса и максимум.
Статистика навыков/вопросов использует fraction, а не 20/30/50 баллов.

2. ПРЕДВАРИТЕЛЬНЫЕ ПРОВЕРКИ
Файлы: backend/app/api/routers/testing.py, app/services/testing_service.py,
app/schemas/testing.py (все внутри backend/).
POST /api/testing/attempts/{id}/check: item_id + code.
На каждую задачу 10 проверок. Счётчик сохраняется в JSON заданий попытки.
Проверяются владелец, статус и срок попытки; PostgreSQL использует блокировку строки.
Проверка не завершает попытку и не меняет профиль. Итоговая сдача проверяет код
из текущего answers, не лучший код предыдущих проверок.
В API добавлены difficulty, base_weight, bonus_weight, max_score, checks_used/limit.
Ответы и скрытые тесты не выдаются. Новый публичный пример соответствует данным
сгенерированной задачи. Миграция БД для этих добавлений не нужна.

3. БАНК, ПРЕДПРОСМОТР И НАСТРОЙКИ
bank.py: 60 новых шаблонов из актуальной ветки; старый банк не выбирается.
Удалён неиспользуемый app/testing_bank/ml_variants.py.
app/services/vacancy_service.py: предпросмотр под вакансию показывает 3 задачи
целевого грейда. app/core/config.py и .env.example: число задач по умолчанию 3.
Грейды Intern/Junior/Middle/Senior, направления Backend/Frontend/DS/QA/DevOps.
Решение о грейде, cooldown, история, авторизация и защита контактов остаются
в существующей бизнес-логике — ML не меняет профиль самостоятельно.

4. ЗАПУСК И СОСТАВ MAIN
docker-compose.yml включает frontend, backend, db, mailpit.
ML_SERVICE_URL пуст: ML встроен в backend. Отдельный сервер 8001 не нужен.
Ключ GIGA_TOKEN необязателен; хранится в корневом .env, не в Git.
Убраны старые комментарии про отдельный ML и обязательный reset.
PostgreSQL наружу не опубликован; локальные сервисы привязаны к 127.0.0.1.
Файлы frontend не заменять кодом из старых архивов.
Первый запуск: docker compose up -d --build, затем seed без --reset.
При обновлении сохранённой базы seed --reset НЕ обязателен и удаляет тестовые записи.
health.version остаётся 1.4.0; build меняется от содержимого кода, миграция 0006.

5. ПРОВЕРКИ И ДОКУМЕНТАЦИЯ
169 тестов прошли локально на SQLite. PostgreSQL/миграции проверяет CI, его новый
результат нужно смотреть после публикации. Docker на машине сборки не запускался.
Эталонные решения: backend/scripts/verify_hybrid_testing.py.
Тесты: tests/test_contest_generation.py, test_contest_scoring.py,
test_all_contests.py, test_code_checks.py и существующий suite.
scripts/evaluate.py оставлен для синтетической оценки, не как доказательство
качества на реальных кандидатах. docs/04_validation.md не содержит старых
неподтверждённых процентов, нагрузки и утверждений об абсолютной защите.

6. ЧТО ПРОВЕРИТЬ/ДОРАБОТАТЬ ДАЛЬШЕ
Завтра — docs/QA_CHECKLIST.md: таймер, конкурентные проверки, согласия,
баллы в истории/профиле/поиске, PostgreSQL, миграции, clean Docker start.
Промышленный запуск требует отдельной безопасной песочницы, HTTPS/prod-секретов
и подтверждённых внешних интеграций. Subprocess/AST не объявлен безопасной
песочницей; скрытые тесты не подтверждают заявленную сложность O(...).
Не переписывайте историю и не сбрасывайте базу без необходимости.
