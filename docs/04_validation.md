# 4. Процедура валидации и результаты

Датасетов и эталонной разметки организаторы не дают: процедуру предлагает команда. Наша процедура
**воспроизводима одной командой** и прогоняет **настоящий код продукта**, а не его упрощённую копию:
банк заданий, движок тестирования и ранжирование.

```bash
cd backend
python -m scripts.evaluate      # отчёт: scripts/output/evaluation.md и evaluation.json (фиксированный seed = 42)
python -m scripts.load_test     # нагрузка на поднятом стенде: scripts/output/load_test.md
```

## Эталон: синтетическая популяция с известным уровнем

Мы генерируем кандидатов, у которых **заранее известен истинный уровень** θ. Это и есть эталонная разметка:
истинный грейд = ⌊θ⌋, где [1,2) — Junior, [2,3) — Middle и т.д.

**Модель ответа на задание** — IRT 2PL (стандарт психометрии): `P(верно) = 1 / (1 + e^(−1.7·(θ − (уровень − 0.75))))`.
Сильный кандидат чаще решает сложные задания, но иногда ошибается; слабый иногда угадывает.

**Поведение кандидата** — по правилам продукта: заявляет грейд (в 40% случаев ошибается на ±1), проходит тест;
не прошёл — пробует уровнем ниже; прошёл на 90%+ — пробует выше.

## Часть A. Тестирование: отличает ли тест грейды

400 кандидатов, тест из 10 заданий:

| Метрика | Значение | Что значит |
|---|---:|---|
| Точность грейда | **72.3%** | Тест поставил ровно истинный грейд |
| То же вдали от границы грейдов | **77.4%** | Ошибки в основном у кандидатов «на стыке» двух грейдов |
| Точность ±1 грейд | **92.0%** | Грубых ошибок (через грейд) — 8% |
| Повторное прохождение даёт тот же грейд | **61.5%** (±1: 89.2%) | Другой вариант теста, тот же человек |
| Средняя дискриминативность заданий (r_pb) | **0.65** (минимум 0.44) | Каждое задание отличает сильных от слабых; > 0.3 считается хорошим |
| Средний балл теста Middle по истинному грейду | Intern 27 · Junior 56 · **Middle 81** · Senior 96 | Разделяющая сила: соседние грейды получают заметно разные баллы |
| Без грейда (провалил всё) | 7.7% | Кандидаты уровня ниже Intern |

**Устойчивость к утечке ответов.** Если кандидат получил ключ ответов от чужого варианта, его средний балл —
**31%**. При фиксированном тесте с утёкшим ключом было бы 100%. Параметризация шаблонов делает пересылку
ответов бесполезной: это обязательное требование организаторов («одинаковые задачи не должны расходиться»).

**Длина теста:**

| Заданий | Точность | Согласованность |
|---:|---:|---:|
| 6 | 74.8% | 62.3% |
| 10 | 72.3% | 61.5% |
| 14 | 71.3% | 68.5% |

Точность почти не растёт с длиной: она упирается в кандидатов на стыке грейдов. 10 заданий — компромисс между
надёжностью и временем (≈15–20 минут). Для жюри можно временно поставить `TEST_QUESTIONS_COUNT=6` (экспресс-тест).

## Часть B. Подбор: лучше ли он поиска по ключевым словам

900 кандидатов, 40 вакансий. Резюме «врёт»: кандидат дописывает 0–4 навыка, которых не знает; тест отражает
истинный уровень. **Релевантный кандидат** = нужная специализация, истинный грейд вакансии и истинный стек,
покрывающий не менее 60% навыков вакансии.

| Ранкер | Precision@10 | nDCG@10 | Доля верного грейда в топ-10 |
|---|---:|---:|---:|
| **Наш (тест + стек + ФСП + активность + текст)** | **0.278** | **0.316** | 60.5% |
| «Классический джоб-сайт»: совпадение ключевых слов резюме | 0.210 | 0.239 | 29.2% |
| Только балл теста | 0.160 | 0.168 | 65.5% |

Наш ранкер находит релевантных кандидатов **на 32% чаще**, чем поиск по ключевым словам (P@10 0.278 против 0.210),
и вдвое чаще ставит в топ людей правильного грейда. Сортировка только по тесту хорошо угадывает грейд, но
игнорирует стек, поэтому её точность ниже.

## Часть C. Нагрузка: «десятки одновременных пользователей»

`scripts/load_test.py`: 50 одновременных виртуальных пользователей в течение 30 секунд. Половина — работодатели
(подборка под вакансию, поиск по категории, карточка кандидата), половина — кандидаты (профиль, приглашения,
вакансии). База — демо-данные (200 кандидатов).

| Показатель | Значение |
|---|---|
| Запросов за 30 с | 3078 (**≈100 в секунду**) |
| Ошибок | **0** |
| Подборка под вакансию — медиана / 95% | 330 / 1076 мс |
| Поиск по категории — медиана / 95% | 311 / 1153 мс |
| Карточка кандидата — медиана / 95% | 228 / 1092 мс |
| Без нагрузки (один запрос) | подборка 20–80 мс, профиль 6–16 мс |

Замер сделан на **2 vCPU**, где на тех же двух ядрах работал и сам генератор нагрузки. На стенде жюри (около 8 CPU)
задайте `WEB_CONCURRENCY=8`, и время ответа заметно уменьшится. В ходе замера найдено и исправлено узкое место:
карточки выдачи проверяли «основание раскрыть контакты» отдельным запросом на каждого кандидата (44 SQL-запроса на
подборку). Теперь это 2 запроса на страницу, всего 6, а подборка ускорилась примерно вдвое.

## Автотесты

78 автотестов API (`pytest`) проходят на SQLite и PostgreSQL. Они покрывают регистрацию, вход, роли, правила
грейда, видимость контактов, приглашения, ФСП (в том числе случай без истории), вход через FSP ID, ATS, контракт с ML-частью,
шифрование и защиту от перебора паролей.

## Ограничения (честно)

- Популяция синтетическая: абсолютные числа зависят от модели ответа. Модель стандартная (IRT 2PL), параметры
  и seed зафиксированы, всё пересчитывается одной командой.
- Повторное прохождение даёт тот же грейд в 61.5% случаев. Основной источник расхождений — кандидаты на стыке
  грейдов. Следующий шаг — адаптивный добор заданий в «серой зоне» (68–75%).
- Реальных кандидатов для калибровки нет. Статистика по каждому заданию (`question_stats`) уже копится,
  и на реальных данных веса и сложность можно будет откалибровать.
